# قواعد المنفذ (تنطبق على كل خطوة)

اقرأ هذا الملف كاملاً قبل أي عمل. ثم اقرأ ملف الخطوة، ثم الأقسام المذكورة منه من `docs/plans/secure-sending-plan.md`.

## 1. النطاق
1. نفّذ **ما في ملف الخطوة فقط**. لا تضف ميزات، ولا تُعد هيكلة ملفات غير مذكورة، ولا "تحسّن" شيئاً بجانب الطريق.
2. إذا اكتشفت مشكلة خارج النطاق أو تعارضاً مع الخطة: **لا تصلحها**. اكتبها في التقرير تحت "ملاحظات خارج النطاق".
3. إذا لم تستطع تنفيذ بند (غموض، أداة ناقصة، فشل غير متوقع): توقف عنده، اكتب السبب بدقة في التقرير، وأكمل البنود المستقلة عنه فقط.
4. ممنوع الافتراض بصمت. ما لا تعرفه اكتبه "غير معروف" في التقرير.

## 2. الأمان (ممنوعات مطلقة)
- لا `git push`، ولا نشر، ولا اتصال بالسيرفر الحقيقي، ولا استدعاء Firebase/FCM الحقيقي، إلا إذا طلب ملف الخطوة ذلك حرفياً.
- لا `git reset --hard`، ولا `git clean`، ولا `git checkout -- .`، ولا `git stash drop`، ولا حذف ملفات لم تنشئها أنت.
- لا تطبع قيمة أي سر في الشاشة أو التقرير أو الـ commit: مفاتيح API، `private_key`، `.env`، محتوى `credentials/*.json`.
  إذا لزم الإشارة لسر اذكر **المكان فقط** (مسار الملف ورقم السطر) دون القيمة.
- لا تضف ملفات أسرار إلى git. لا تعدّل `.env` ولا `credentials/` ولا `data.db`.
- لا تثبّت اعتماديات جديدة إلا ما نص عليه ملف الخطوة.

## 3. Git
- مستودع `fcm_microservice`: اعمل على الفرع المحدد في الخطوة. commit واحد (أو أكثر عند الحاجة) بصيغة Conventional Commits
  `<type>(<scope>): <ID> <ملخص بالإنجليزية ≤72 حرفاً>` وسطر `Refs: docs/plans/secure-sending-plan.md <ID>`.
  أضف سطور الإسناد التي تحددها بيئتك. أضف الملفات **بالاسم** (`git add path`) لا `git add .`.
- مستودع `taqati`: اتبع `taqati/AGENTS.md`. **لا تنفّذ `git commit` ولا `git push`** إلا إذا طلب ملف الخطوة ذلك صراحة.
  بدلاً من ذلك اكتب في التقرير رسالة commit جاهزة وأمر `git add` بالملفات المعنية، بالصيغة في القسم 8 من AGENTS.md.
  وقبل أي تعديل في taqati اقرأ `taqati/TODO.md` وغيّر حالة المهمة كما يطلب AGENTS.md القسم 0 (إذا كانت الخطوة تعدّل كوداً).

## 4. الجودة
- Rust: `cargo fmt` على الملفات التي عدلتها، `cargo build` بلا تحذيرات جديدة، `cargo clippy` بلا تحذيرات جديدة، `cargo test` كامل.
  إذا فشل اختبار كان فاشلاً **قبل** عملك، سجّله كـ"فشل سابق" ولا تصلحه.
- لكل سلوك جديد اختبار. اختبارات "طريقة الفحص" في الخطة تُكتب كما هي بأسماء واضحة.
- لا تعطّل اختباراً ولا تضعف assertion لتنجح. إذا كان الاختبار يتعارض مع الخطة، اكتب ذلك في التقرير.
- الأخطاء تُدار بـ fail-closed (المبدأ 7 في الخطة). لا `unwrap()` على مدخلات خارجية.

## 5. التقرير (إلزامي، ملف واحد)
اكتبه في `docs/plans/reports/<ID>-report.md` (أنشئ المجلد). **بالأرقام والمخرجات الفعلية لا بالانطباعات**.

```
# تقرير <ID>
- التاريخ/الوقت:
- الفرع و HEAD قبل/بعد (git rev-parse --short HEAD):
## 1. ما نُفِّذ (بند بند من ملف الخطوة)
| البند | الحالة (تم / جزئي / لم يتم) | ملاحظة |
## 2. الملفات (git diff --stat بعد العمل، ولكل ملف جديد سطر شرح)
## 3. الأوامر التي شغلتها ونتائجها (مخرجات مختصرة حقيقية: عدد الاختبارات ناجح/فاشل، أخطاء/تحذيرات)
## 4. طريقة الفحص: كل بند من "طريقة الفحص" في الخطة/الخطوة ← النتيجة الفعلية وكيف تحققت
## 5. انحرافات عن الأمر (وسببها)
## 6. ملاحظات خارج النطاق
## 7. أسئلة للمالك/المراجع
## 8. حالة git النهائية (git status --short و git log --oneline -5)
```
لا تكتب "تم بنجاح" بدون دليل في القسم 3 أو 4. لا تُخفِ فشلاً.
