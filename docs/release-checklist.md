# قائمة النشر والتحقق (Release Checklist)

قائمة إرشادية وتدقيقية للمالك وفريق العمليات قبل وأثناء وبعد نشر التحديث
المبني على خطة الإرسال الآمن (المراحل R1 إلى R6 والقسم 7).

---

## 1. مرحلة ما قبل النشر (Pre-deployment)

- [ ] **نسخة احتياطية لقاعدة البيانات:**
  أخذ نسخة متسقة من `data.db` باستخدام أمر SQLite الآمن:
  ```bash
  sqlite3 data.db ".backup pre_release_$(date +%Y%m%d_%H%M%S).db"
  ```
- [ ] **توثيق الحالة السابقة:**
  تسجيل إصدار Git النشط على السيرفر حالياً:
  ```bash
  git rev-parse HEAD > /backups/last_working_commit.txt
  ```
- [ ] **مراجعة متغيرات البيئة (`.env`):**
  - [ ] `CORS_ALLOWED_ORIGINS` يحتوي على أصل لوحة التحكم الصريح (مثل `https://admin.example.com`).
  - [ ] `TRUST_PROXY=true` مفعّل إذا كان الخادم خلف Reverse Proxy.
  - [ ] `COOKIE_SECURE=true` مفعّل لبيئة الإنتاج HTTPS.
  - [ ] `LEGACY_API_KEY_ENABLED=true` أثناء مرحلة الانتقال الأولى R1 للتوافق مع التطبيقات القديمة.
  - [ ] `CREDENTIALS_DIR` يشير لمجلد قابل للكتابة من قِبل الحاوية.
- [ ] **بناء واختبار الصورة:**
  التأكد من نجاح اختبارات البناء واكتمال حزمة الواجهة `dist/` دون أخطاء.

---

## 2. النشر والتشغيل الأولي (Deployment & Initialization)

- [ ] تشغيل الحاوية الجديدة عبر `docker compose up -d`.
- [ ] مراجعة سجلات الإقلاع: التأكد من تشغيل التهجيرات (Migrations) التلقائية وظهور رسالة الاستماع على المنفذ.
- [ ] إنشاء حساب المالك (إذا كانت هذه أول مرة لتشغيل النظام):
  ```bash
  docker compose exec fcm_microservice fcm_microservice create-owner --email owner@example.com
  ```
- [ ] تسجيل الدخول كمالك وتغيير كلمة المرور المؤقتة فوراً.
- [ ] استيراد أو مراجعة تكوينات التطبيقات (مثل `policies/watt.example.json`) من لوحة التحكم والتأكد من ظهور القوالب مفعّلة.

---

## 3. فحوصات ما بعد النشر حسب الأدوار (Post-deployment Checks)

تحقق من سلوك النظام باستخدام حسابات تجريبية مخصصة لكل دور (دون كشف أسرار):

### 3.1 حساب الأدمن (`admin`)
- [ ] تسجيل الدخول للوحة التحكم: تظهر جميع التبويبات (التطبيقات، المستخدمون، التدقيق).
- [ ] إرسال إشعار تجريبي عبر قالب `admin_alert`: يصل بنجاح.
- [ ] إجراء إرسال حر (`POST /admin/apps/:app/send`): يتطلب تأكيداً ويرسل بنجاح.

### 3.2 حساب الشركة المعتمدة (`company - approved`)
- [ ] إنشاء حملة تسويقية عبر `POST /api/v1/campaigns`: تُقبل وتدخل حالة `pending_review` (أو `sent` إذا تجاوزت حد أول 3 حملات).
- [ ] استعلام قائمة حملات الشركة عبر `GET /api/v1/campaigns`: تظهر الحملة التابعة للشركة فقط.
- [ ] استعراض بطاقة الحملة في لوحة التحكم: تظهر الحصة المتبقية للشركة `company_quota_remaining`.

### 3.3 حساب الشركة غير المعتمدة أو المعلقة (`company - pending / unapproved`)
- [ ] محاولة إنشاء حملة تسويقية: تُرفض فوراً بـ **`403 Forbidden`** (شرط `require: {"status": "approved"}`).

### 3.4 حساب المستخدم العادي (`user`)
- [ ] تسجيل جهاز عبر `POST /api/v1/devices/register` بتوكن المستخدم: يرد `{"status":"ok"}`.
- [ ] إرسال قالب مشروط مثل `order_new`:
  - عندما يكون المرسل هو المشتري الفعلي: يُسلَّم الإشعار (`200 OK`).
  - عندما يحاول مستخدم آخر إرسال إشعار عن نفس الطلب: يُرد فوراً بـ **`403 Forbidden`**.

### 3.5 حساب الفني (`technical`)
- [ ] التحقق من صلاحيات قوالب الفنيين وعدم قدرتهم على إرسال حملات تسويقية للشركات.

## 4. قائمة الفحص البصري للوحة التحكم (Dashboard Visual Inspection)

- [ ] **القوالب:**
  - تظهر قائمة القوالب بحالتها ووصفها.
  - زر "قالب جديد" يفتح المحرر، وإدخال خطأ يُظهر رمز الخطأ والرسالة بجانب الحقل فوراً.
  - المعاينة تعرض النص النهائي كنص خام وليس كـ HTML.
  - الإرسال التجريبي معطّل لمن ليس لديه `test_uid` مربوط بحسابه.
- [ ] **الحملات وطابور المراجعة:**
  - ظهور نصوص الجمهور بصيغة مفهومة (مثل "المستخدمون في العراق").
  - ظهور بطاقة الحصة المتبقية للشركة `company_quota_remaining` مع تنبيه لوني عند نفاد الحصة (0).
  - زر الرفض معطّل حتى كتابة سبب الرفض.
- [ ] **سجل الإرسال (Send Log):**
  - عمل مرشحات `kind` و`status`.
  - عمل مرشح `ref` (مطابقة تامة للخلفية).
  - عمل مرشحي التاريخ `since` و`until`.
  - إدخال تاريخ غير صالح يُظهر رسالة خطأ عربية واضحة.
- [ ] **سجل التدقيق (Audit):**
  - المالك يرى سجلات كافة التطبيقات.
  - المدير يرى سجلات تطبيقاته المربوطة فقط حتى دون تحديد تطبيق في المرشح.
  - اختيار تطبيق غير تابع للمدير يمنع الوصول (`403`).

---

## 5. الفحص الأمني النهائي (Security Verification)

- [ ] **المفتاح القديم:** تجربة `POST /api/v1/send` بالمفتاح القديم والتأكد من تسجيل التحذير، وتجربة تجاوزه لحد السرعة للتأكد من رد `429`.
- [ ] **مفتاح تطبيق ملغى:** إنشاء مفتاح تطبيق تجريبي، إلغاؤه من الداشبورد، ثم استدعاء `/api/v1/send/template` به والتأكد من رد **`401 Unauthorized`** فوراً.
- [ ] **تعطيل تطبيق:** تعطيل تطبيق من شاشة إعدادات التطبيق، والتأكد من أن أي محاولة إرسال للتطبيق تُرد بـ **`404 Not Found`** فوراً.
- [ ] **رفع ملف Service Account غير صالح:** محاولة رفع ملف JSON تالف أو لا يخص حساب خدمة في Google، والتأكد من رفضه عبر الفحص الحي ورده بـ `400 Bad Request`.
- [ ] **مراجعة الحزمة:** التأكد عبر `grep` من عدم وجود أي مفاتيح خاصة أو أسرار حقيقية في ملفات الـ bundle أو التقرير.

---

## 6. إجراءات التراجع في الطوارئ (Emergency Rollback)

إذا ظهر خلل غير متوقع بعد النشر:
1. إيقاف تشغيل الحاوية الحالية:
   ```bash
   docker compose down
   ```
2. استعادة نسخة قاعدة البيانات السابقة:
   ```bash
   cp /backups/pre_release_*.db ./data/data.db
   ```
3. إعادة تشغيل إصدار الحاوية السابق المثبت في `last_working_commit.txt`.
4. التحقق من عودة الخدمة والعمل بالنظام القديم.
